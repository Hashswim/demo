# 개발 순서

1. 가상 데이터와 평가 정답 합의: data/*.json, 역할별 실제 수행 업무와 프로젝트 기술을 구분. gold는 검색 인덱스에 포함하지 않는다.
2. 브라우저 UI: npm dev, 2개 역할과 전체 업무 흐름 확인. 수정할 UI는 apps/web/src/views 단위.
3. Compose 기준선: 인증·권한, 프로필, 요청·작업, 추천, 후보 저장, 평가까지 실제 DB 흐름 실행.
4. 추천 평가: MES 별칭, Java/JavaScript 혼동, PM 개발 경력 오인, 이력 부재, 미확인 투입 상태, 중복 이력의 순위 영향 점검.
5. 모델 연결: GGUF와 임베딩 파일·리비전·라이선스 준비. local 모드에서 JSON 유효성·한국어 품질·응답 시간·최대 RSS 측정. baseline과 같은 gold로 비교.
6. 근거 검토: 정확한 원문·이력 ID, 근거가 요건을 지지하는지 별도 사람이 검토. 모델 설명의 의미 정확도는 자동 원문 검사만으로 보장하지 않는다.
7. 운영 보강: 작업 중단·재시도 실DB 시험, 모델 요청 큐 공유(현재 API/Worker 동시 추론 가능), 감사 적재, 변경된 이력의 과거 추천 경고, 사용자·권한 관리 절차.
8. EKS 사전 검사: Terraform validate/견적, Helm lint/template, IAM·TLS·Secret·이미지 digest·데이터 ConfigMap·모델 PVC 준비. AWS 생성은 별도 실행.
9. 짧은 EKS 검증: 운영 시간 기록, 외부 공개 범위 점검, 단일 CPU 노드 자원과 실제 비용 확인.
10. 복구 시험: 별도 DB로 복원, 로그인·요청·추천·후보 확인, 운영 DB 대체 전 검증. 예산 내 종료 후 잔여 EBS·IPv4·스냅샷·로그 확인.

실제 의미 검색·LLM 결과는 local 모델 파일을 준비한 뒤 검증해야 한다. 현재 기준선의 점수는 모델 성능 지표가 아니다. 운영 환경 배포 완료·보안 인증·상시 서비스 준비 완료를 의미하지 않는다.
